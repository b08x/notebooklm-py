# Facts

- The Compiler view (p) lists the audio project YAMLs in examples/notebooklm-audio/projects/ and shows the title of the notebook currently selected in the sidebar as the target.
- Pressing Enter on a YAML compiles it against the selected sidebar notebook. The YAML's notebook_id is ignored, and the YAML file is not modified.
- When the YAML has auto_extract: true, the template slots (four lexical states, topics, escalations) are filled in the background from the notebook's ingested clauses, while the TUI shows a spinner. If the notebook has no ingested clauses, NotebookLM chat (auto_bind.py) is used instead, with a warning. If both fail, the YAML's own values are used, with a warning.
- The preview panel shows the full compiled prompt, scrollable with j/k. Its header shows the project, the target notebook, audio_format, audio_length, and the character count.
- The character count turns to a warning color above 5,000 characters. It is only a warning and does not block sending.
- Pressing e opens the compiled prompt in $EDITOR (falling back to nvim, then vi). After the editor exits, the preview shows the edited text marked 'edited', and the edit is not written back to the YAML or the template.
- Pressing g opens a confirmation panel showing notebook title, project, format, length, character count, and edited status. Pressing y sends the prompt. Pressing n or Escape cancels, and no request is made.
- The text sent to NotebookLM is exactly the prompt shown in the preview, including any edits. Generation uses the YAML's audio_format and audio_length.
- Generation runs in the background. The TUI stays responsive, and the Compiler view shows the state (submitted / generating / downloading / done / failed) and the elapsed time.
- When generation finishes, the MP3 is saved to ~/Archive/NotebookLM/audio/<project-slug>/<YYYYMMDD-HHMM>_<notebook-slug>.mp3 and the path is shown in the TUI.
- Every generation writes a sidecar <same-name>.json next to the MP3: project YAML path, template name, notebook id and title, artifact id, format, length, the exact prompt sent, edited flag, and start/finish timestamps. Failed generations also write a sidecar, with the error.
- If generation fails, times out, or is rate-limited, the TUI shows the error and artifact id. The prompt, including any edits, is kept so that pressing g retries without recompiling or re-editing.
- runner.py --emit -n <notebook> prints only the compiled prompt (after auto-bind) to stdout, so it can be piped into `notebooklm generate audio --prompt-file -`.
- runner.py --execute passes the YAML's audio_format and audio_length to generate_audio. Previously these were ignored.
- The Compiler view follows the Charm-style look using tui/theme.py tokens: rounded panel borders, one accent color for the selected YAML and key hints, dimmed metadata lines, and consistent padding.
- The footer shows Compiler-view key hints (Enter compile, e edit, g generate, j/k scroll, Esc back), and docs/tui-reference.md documents them.
- Out of scope: transcript/script molding and local TTS (goals/audio-script-molding), video compiler generation, moving the compiler out of examples/, batch or variant generation, and regenerating failed artifacts.
- Retrieval for each slot is hybrid: a Postgres full-text query (the existing idx_clauses_tsv GIN index) and a pgvector similarity query over the notebook's clauses are merged by Reciprocal Rank Fusion (k=60) into one ranked list.
- Each filled slot records the clause ids and text it was derived from. The preview shows the supporting clauses under the prompt, and the sidecar JSON stores them per slot.
- The LLM call that turns retrieved clauses into slot values runs in the worker thread under dspy.context(lm=...) with the LM captured on the main thread. dspy.configure() and setup_dspy_router() are never called from the worker.
